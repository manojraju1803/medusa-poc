## Custom commerce logic in this POC

This is a Medusa DTC Starter (see AGENTS.md) customized for a B2B buyer-approval, tiered-pricing, and Indian GST flow. Beyond the starter scaffolding, four pieces of real logic exist — three ride on stock Medusa modules and their extension points (middlewares, workflow hooks), the fourth (`src/modules/india-gst-tax/`) is this repo's first custom module, needed because tax providers have no hookable extension point:

- **`apps/backend/src/api/middlewares.ts`** — the only file defining custom API middleware. Two concerns, both keyed off membership in a customer group literally named `"Approved"` (`isApproved()` in that file):
  - `hidePrices` strips any `calculated_price`-containing field from `queryConfig.fields` when the caller isn't approved, on the `GET /store/products*` / `/store/product-variants*` routes and — since `/store/product-categories*` and `/store/collections*` accept the same `?fields=*products.variants.calculated_price` expansion and were found unguarded — on those four routes too (8 total).
  - `requireApproved` hard-blocks cart create/read/update/line-item/complete routes for anyone not approved, since cart line items carry `unit_price` directly (not filterable via `?fields=`).
  - The group name is a hardcoded string constant (`APPROVED_GROUP`) — renaming that group in the admin UI silently disables both gates.

- **`apps/backend/src/workflows/hooks/`** — one file per hook consumer, auto-loaded (Medusa's `WorkflowLoader` recursively imports everything under `src/workflows` at boot; nothing here is manually registered):
  - `add-to-cart.ts`, `create-cart.ts`, `update-line-item-in-cart.ts`, `complete-cart.ts` (+ `utils/assert-minimum-quantity.ts`) enforce a per-variant minimum order quantity read from `variant.metadata.min_quantity`, via each workflow's `hooks.validate`. These only throw — never mutate the requested quantity, because `completeCartWorkflow` builds the order from a pre-hook snapshot, so any in-hook correction there would be silently discarded.

- **`apps/backend/src/migration-scripts/customer-group-quantity-pricing-seed.ts`** — seeds two customer groups (`Manufacturer`, `Customer`; renames the older `Trader`/`Consumer` if present), each with its own price list carrying 3 quantity slabs on the same variant. Price-list prices set `min_quantity`/`max_quantity` as **top-level fields**, not nested under `rules` — the admin dashboard's price-list editor does the latter, which the pricing engine's SQL never reads, silently defeating every tier. Run it the same way as `initial-data-seed.ts` (see AGENTS.md's Database commands): `npx medusa exec ./src/migration-scripts/customer-group-quantity-pricing-seed.ts` from `apps/backend`. Note: `src/migration-scripts/*` is gitignored except `initial-data-seed.ts`, so this and the other seed scripts named in this file exist only in the original working copy, not in a fresh clone; a clone of the shared database already contains their results.

- **`apps/backend/src/modules/india-gst-tax/`** — a custom `ITaxProvider` (`service.ts`, registered via `index.ts`'s `ModuleProvider()` and wired into `medusa-config.ts`'s `modules` array under `@medusajs/medusa/tax`) that splits GST into CGST+SGST (intra-state) or IGST (inter-state), decided by the buyer's shipping province (`context.address.province_code`, which must be the full lower-case ISO 3166-2 code, e.g. `"in-ka"` — a bare state code like `"KA"` never matches) against the seller's own state (Karnataka, baked into the provider's `options.sellerProvinceCode` since `TaxCalculationContext` carries no seller address at all). A provider module was required, not a workflow hook: `ITaxProvider` has no `AbstractTaxProvider` base class and no hookable extension point — it's a standalone class registered directly with the tax module. The GST **percentage** is deliberately *not* looked up by the provider itself — a module provider's constructor runs in the tax module's own isolated DI container (confirmed empirically: resolving `query`, or any other module's service, throws `AwilixResolutionError: Could not resolve 'query'` at request time). Instead, per-product `TaxRate` rows with a `TaxRateRule` (`reference: "product"`, `reference_id: <product_id>`, no `metadata` involved) are seeded in the India `TaxRegion`, and the tax module itself pre-matches them before calling the provider — the same pattern the stock `system` provider uses. The provider only decides the CGST/SGST/IGST split; the rate is "configuration, not hardcoded" in the form of those seeded `TaxRate` rows. Deliberately **not** keyed by HSN either — GST is a tax-class WooCommerce assigns directly per product, with no HSN dependency. A line item that matches no `TaxRate` at all throws and blocks checkout rather than guessing. Seeded in two steps: `apps/backend/src/migration-scripts/india-gst-tax-region-seed.ts` (India region/tax-region/shipping infra, plus the first per-product rates) and then `real-catalogue-gst-tax-rates-seed.ts`, which attaches the real catalogue's GST classes (18/12/5/0%) to every imported product. The 18% rate is deliberately `is_default: true`: products with no GST class in the source data fall back to it, so in the India region the provider's no-rate throw only fires if that default rate is removed.

When extending any of the above, prefer another workflow hook or another middleware route entry over new route-handler logic — that's the pattern the rest of this codebase follows (see AGENTS.md's "Business logic belongs in workflows" convention). The one deliberate exception is a case like the tax provider above, where the extension point Medusa exposes for that concern isn't a workflow hook at all — match whatever the correct stock extension point is for the specific problem, rather than forcing every new concern into a hook.

## Before adding a workaround

Before adding a hook, middleware or custom logic because Medusa "doesn't support" something, check the installed `@medusajs/*` source (`dist/` and `migrations/`) for the current convention. Don't rely on memory or old examples. Verify that the approach is the standard one, not just that the output looks right. Example: price-list rules must use `customer.groups.id`. The old `customer_group_id` was renamed in a 2024 migration, and using it led to a workaround hook, since removed. That key had also kept product pages from showing group prices.
